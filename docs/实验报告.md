## 一、需求分析

### 1.1 要解决的问题

短网址服务看着简单，其实一串完整后端问题都串在里面：URL 校验、唯一短码、
HTTP 重定向、访问日志、统计查询、数据库持久化、部署配置。
它特别适合用来看清一件事——**容器是可以随便删的，业务数据不行**。

### 1.2 需求拆解

| 编号 | 需求 | 验收方式 |
| --- | --- | --- |
| R1 | 输入合法长 URL 能拿到短 URL | 管理台生成后返回短链 |
| R2 | 访问短链能跳回原地址 | 浏览器打开短链，落在 demo.html |
| R3 | 记录访问次数并在界面查询 | 统计抽屉里数字 = 实际 GET 次数 |
| R4 | 界面能列出短链、创建时间和访问数 | 列表页可见 |
| R5 | 非法协议、空输入、重复短码、未知短码有明确反馈 | 各有独立错误码和中文提示 |
| R6 | 容器重建后数据仍在 | `down` + `up` 后短链和次数都保留 |
| R7 | 浏览器和 Git 里都看不到 API Key | 前端全文搜索 + `git check-ignore` |
| R8 | 至少一项自主功能，且真实调用 API | 二维码 / 有效期 / 限流 |
| R9 | 一键启动、停止、备份 | `scripts/` 下四个脚本 |

### 1.3 非目标（明确不做的）

- 不做短链的点击量可视化大屏（实验不要求，5 分钟展示也用不上）。
- 不做用户体系和多租户——本实验是单机课程环境。
- 不对接公网短链服务，全部本地闭环。

## 二、总体设计

### 2.1 三个服务的职责边界

这是本次设计里最需要想清楚的一件事：**谁拥有什么数据，谁调用谁**。

| 服务 | 拥有什么 | 不负责什么 |
| --- | --- | --- |
| `db`（PostgreSQL） | 短链表、访问记录表 | 不做业务判断 |
| `shlink`（Shlink 5.1.6） | 短码生成、302 重定向、访问记录写入 | 不持有我的校验规则，管理 API 要密钥 |
| `web`（自建 Flask） | 页面、校验、限流、密钥 | **不持有短链数据**，也不参与跳转转发 |

### 2.2 关键设计决策

**决策一：浏览器不直接调 Shlink，中间加一层自己的服务。**

理由：Shlink 的管理 API 需要 `X-Api-Key`。如果让浏览器直接调，
密钥就必须下发到前端（F12 一看就有，还能被复制走）。加一层服务端代理后，
密钥只活在 `web` 容器的环境变量里，浏览器只跟我们自己的 `/api/*` 说话。

代价：多一跳网络，多一个要维护的服务。但对本实验来说，
「不泄露密钥」的价值远大于这点开销。

**决策二：短链跳转不经过 `web`。**

理由：跳转是高频路径，让所有访问都穿过 Flask 只会增加延迟和单点风险。
访问者直接打 Shlink 的 8080，统计也在那里写库，更准。
`web` 只负责「管理和查询」，不负责「被访问」。

**决策三：数据放命名卷，不放容器层。**

`shlink-db` 命名卷挂到 `/var/lib/postgresql/data`。
容器、镜像随便重建，卷不动。这是 R6 的实现基础。

**决策四：启动顺序靠健康检查，不靠 `sleep`。**

```yaml
depends_on:
  db:
    condition: service_healthy
```

`sleep 30` 是在猜「30 秒应该够了」，换台慢机器就翻车。
`service_healthy` 是「数据库自己说能接受连接了」，这才是真的就绪。

**决策五：关掉 Shlink 的自动抓标题。**

`AUTO_RESOLVE_TITLES: "false"`。开着的话 Shlink 会去服务器端抓长 URL 的标题，
而我们的长 URL 是 `localhost:9001`——在容器里这个 localhost 是 Shlink 自己，
抓不到还会一直刷错误日志。关掉之后浏览器能访问长 URL 就够了。

### 2.3 长 URL 校验规则（本人新增，上游没有）

| 规则 | 取值 | 理由 |
| --- | --- | --- |
| 协议 | 只允许 `http` / `https` | `javascript:` / `data:` / `vbscript:` 是真实攻击面 |
| 长度 | ≤ 2048 | 浏览器和代理的安全值 |
| 域名 | 必须命中白名单 | 本实验只放开本地/授权目标，防 SSRF |
| 比对方式 | hostname 等于或子域，**不用 `startswith`** | 挡住 `evil-localhost.com` 这类前缀伪造 |

Shlink 本身支持的协议比这宽，所以这条规则**必须由我们自己的接口强制执行**，
这是本次「可辨识的二次开发」的一部分。

## 三、实现要点

### 3.1 代码分层

```
web/
├── peizhi.py           环境变量集中读取（测试可注入）
├── url_yanzheng.py     纯函数校验层，无副作用，最好测
├── xianzhi.py          滑动窗口限流（自主功能③）
├── shlink_kehuduan.py  Shlink REST 客户端，Key 只在这里
└── app.py              Flask 路由，用工厂函数便于测试
```

**为什么 `app.py` 用工厂函数 `chuangjian_app()` 而不是模块级 `app`**：
测试的时候要把「假 Shlink 客户端」塞进去，模块级单例做不到。
这是被逼出来的设计——先写成了模块级，写测试时发现没法注入，才改的。

### 3.2 校验层的设计

返回 `(是否通过, 错误提示)` 二元组，不抛异常。
调用方（`app.py`）不需要记异常类型，直接 `if not tongguo: return 400`。

检查顺序按「先便宜后贵」排：类型 → 空 → 长度 → 解析 → 协议 → 主机 → 白名单。
大部分非法输入在前两步就被拒了，不会走到正则。

### 3.3 限流的实现（自主功能③）

```python
class PinlvXianzhi:
    def yunxu(self, key):
        xianzai = time.time()
        with self._suo:
            duilie = self._jiluo.get(key, deque())
            self._qingli(duilie, xianzai)      # 扔掉滑出窗口的
            if len(duilie) >= self.zuidacishu:
                return False, 0, dengdai
            duilie.append(xianzai)
            return True, shengyu, 0
```

每个 key（这里用客户端 IP）一个 `deque`，存时间戳。
窗口过期的时间戳从头 `popleft()`。用 `threading.Lock` 保证并发安全。

**三个必须写清楚的局限**：

1. **计数在进程内存里**。所以 `Dockerfile` 里 gunicorn 固定 `--workers 1`——
   多 worker 的话每个进程各有一份计数，等于限了个寂寞。
2. **服务重启清零**。
3. **只按 IP 限**。NAT 后面的多个用户会互相影响，这是一刀切的代价。

生产环境应该用 Redis 做共享计数，或者干脆交给 API 网关。
本实验是单机课程环境，进程内实现够用，但**不能吹成生产级**。

### 3.4 前端安全

所有来自接口的文本都经过 `zhuanYi()` 转义，或者直接用 `textContent`。
短链的原网址是用户输入的东西，直接拼 `innerHTML` 就是给自己挖 XSS 坑。
抽屉里的原始访问记录表也是逐条转义后拼的。

### 3.5 Dockerfile 的四个要点

```dockerfile
FROM python:3.12.7-slim          # ① 固定小版本
COPY requirements.txt .          # ② 先拷依赖清单 → 吃缓存
RUN pip install -r requirements.txt
COPY app.py peizhi.py ... ./     # ③ 再拷源码 → 改代码不用重装依赖
COPY templates ./templates
COPY static ./static
RUN useradd ... && chown ...     # ④ 非 root 运行
USER appren
```

②的收益很直观：改一行 Python，重建只要几秒；要是把 `COPY . .` 写前面，
每次改代码都会重装一遍依赖。

## 五、问题与反思

### 5.1 最大的限制：开发机没有 Docker

这是本次实验必须坦白的一点。

指导书对这个口径说得很清楚：「本机没有 Docker，未执行容器启动、短链跳转和数据卷重建，
不将文档核对表述为容器实测。」

我的处理方式：

- **已实测**：`pytest -q` → 68 passed；Compose 变量插值、健康检查语法、
  `depends_on: condition` 对照 5.1.6 文档逐项核对；镜像标签在 Docker Hub 上确认存在。
- **未实测**：容器真正启动、容器重建后数据保留、`ceshi-api.ps1` / `ceshi-bushu.ps1` 的输出。
- 所有未实测的地方都打了 ⚠️ 标记，没有一处写成「实测通过」。

**反思**：如果一开始就先确认环境（`docker version`），
我会选择「原生 Java 路线」或者更早地暴露这个限制，
而不是等到写完 Compose 才发现跑不了。环境确认应该是第 0 步。

### 5.2 限流的方案是被环境逼出来的

理想方案是 Redis 共享计数。但多一个 Redis 容器就多一份资源开销和一份故障面，
而本实验是单机单人场景，进程内内存完全够用。
最后选择了「明确标注局限」而不是「硬上 Redis」——
**能说清边界的不完美方案，比说不清边界的完美方案更适合交作业**。

### 5.3 关于「自主功能」的理解

指导书特别强调：

> 若 Shlink 已内置该能力，必须在本人 Web 中增加新的规则、校验或交互，
> 并用 API 参数真实生效；不能只显示一个静态控件。

这句话点醒了我。二维码和有效期 Shlink 有现成能力，
所以我加了**上游没有的规则**才敢算自主功能：

- 有效期：加了「上限 365 天」，传 400 天会被我们自己的校验挡在调用之前
- 二维码：内容是**短链**而不是长链，这样扫出来的访问照样进统计

并且写了 `test_youxiaoqi_chuandao_kehuduan` 这条测试，
直接断言假客户端收到了 `youxiao_tianshu=7`——
**证明参数真传下去了，不是界面上摆了个控件**。

### 5.4 还没解决的问题

- 限流的多 worker 问题（已用单 worker 绕过，未真正解决）。
- 「按来源/按日期」只算了最近 50 条访问记录，不是全量。
  全量应该在 SQL 层聚合，但 Shlink 的 API 不提供这个，得直接读它的库——
  这又违反了「不跨服务直接改表」的原则，所以先接受这个折中。
- 界面上的列表搜索是**前端过滤当前页**，不是服务端全量搜索。

## 六、收获

1. **镜像 / 容器 / 卷三者的边界**：容器删了业务数据得还在，
   所以数据必须在卷里；配置必须靠环境变量注入；重建容器不该影响业务。
2. **密钥边界的正确画法**：浏览器能看到的都算公开。管理密钥必须留在服务端，
   这是一条不能妥协的线。
3. **`localhost` 在容器里不是宿主机**：这是本实验最经典的坑，
   也是「为什么必须用服务名」的答案。
4. **健康检查 > sleep**：可观测的就绪比猜出来的等待可靠得多。
5. **测试要能被别人跑起来**：先想清楚「别人有没有 Docker」，
   再决定哪些测试要依赖容器。

## 七、思考题

**1. 为什么短网址的重定向状态码选择会影响缓存和统计？**

301 是永久重定向，浏览器和中间代理会长期缓存，之后改短链指向可能不生效，
而且后续访问可能根本不回源，统计不到。302 是临时重定向，
每次都会回源，改指向立刻生效，访问也能被如实记录。
短链服务的指向天然可变，所以用 302。

**2. 命名卷与 bind mount 怎么取舍？**

| 维度 | 命名卷 | bind mount |
| --- | --- | --- |
| 备份 | `docker run --rm -v 卷:/data alpine tar` 即可，路径稳定 | 直接拷宿主目录，但要处理权限 |
| 可移植性 | 跨平台一致，Docker 管路径 | 依赖宿主路径，换机器要改 |
| 可观察性 | 要进容器或临时容器才看得到 | 宿主上直接 `ls` 就能看 |

本实验选命名卷：数据是数据库的，我不需要直接翻文件，备份脚本用 `pg_dump` 走逻辑导出。

**3. 怎么防止短链被用于恶意跳转，同时不误封合法 URL？**

用**白名单**而不是黑名单。黑名单永远列不全恶意域名，而且会误伤。
白名单的代价是「没提前放开的合法地址也用不了」——
在课程环境里这个代价可以接受，对外发布时应该改成
「协议 + 域名信誉 + 频率限制 + 人工申诉」的组合。

**4. 健康检查、`depends_on` 与应用级重试分别解决什么？**

三者管的是不同时间段：

| 机制 | 管什么 | 例子 |
| --- | --- | --- |
| 健康检查 | 「服务自己说它行了」能否被观测 | Shlink 起来后 `/rest/health` 返回 pass |
| `depends_on: condition` | 启动**顺序** | db 没 healthy 就不起 shlink |
| 应用级重试 | 运行期的**瞬时抖动** | Shlink 偶发 502 时 Web 重试一次 |

它们**不能互相替代**。用 `sleep 30` 顶替 `depends_on` 是在猜。
